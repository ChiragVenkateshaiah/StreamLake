# StreamLake Kafka Debugging Guide
---

## Executive Summary
This document captures the complete debugging journey of establishing an end-to-end Kafka -> GCS ingestion pipeline for the StreamLake project. Over 6 hours of debugging revealed five critical failure modes in distributed streaming systems, each with specific root causes and resolutions.

**Key Insight**: Streaming systems fail more often due to misunderstood semantics (connection readiness, serialization contracts, authentication scope) than missing code.

The issues encountered represent real production-grade failure modes in Kafka-based systems and are documented here for future reference when working on distributed systems.

## Issues Encountered
- Issue 1: Connection Refused - Kafka Not Ready
- Issue 2: Missing CLUSTER_ID in KRaft Mode
- Issue 3: Bytes Not JSON Serialization
- Issue 4: GCS 403 Forbidden - Authentication Scopes
- Issue 5: Kafka Crash Loops - Memory Pressure

## Issue 1: Connection Refused - Kafka Not Ready
### Symptom
Consumer script failed immediately with connection refused errors when attempting to connect to Kafka on 127.0.0.1:9092
```bash
%3|...|FAIL|rdkafka#consumer-2| [thrd:127.0.0.1:9092/bootstrap]: Connect to ipv4#127.0.0.1:9092 failed: Connection refused
```
### Root Cause
KRaft mode (Zookeeper-free Kafka) requires significantly more initialization time than traditional Zookeeper-based Kafka. The consumer was attempting to connect before Kafka had completed its metadata initialization and was ready to accept client connections.

**Critical Insight**: 'docker compose up -d' only means the container started, not that the service inside is ready. KRaft initialization includes formatting the metadata log, electing a controller, and loading topic metadata - all of which take 20-30 seconds.

### Solution
Implemented a retry mechanism in the consumer class that actively probes Kafka readiness before attempting subscription:

```python
def _wait_for_kafka(self):
    for attempt in range(1, KAFKA_READY_RETRIES + 1):
        try:
            self.consumer.list_topics(timeout=2)
            print(f'[✓] Kafka is ready (attempt {attempt})')
            return
        except KafkaException:
            time.sleep(KAFKA_READY_DELAY_SEC)
```
#### Why list_topics() Works
- Performs actual TCP handshake with broker
- Fetches metadata from Kafka (not just port check)
- Uses same bootstrap.servers config as actual consumption
- Fails fast if Kafka is not genuinely ready

#### Prevention for Future
- Always implement retry logic in Kafka clients (producer and consumer)
- Never assume container 'up' status equals service readiness
- Use active probing (list_topics, broker metadata) rather than sleep timers
- Document expected boot times for KRaft mode in deployment runbooks

## Issue 2: Missing CLUSTER_ID in KRaft Mode

### Symptom
Kafka container entered crash loop immediately after starting. Docker logs showed repeated failure with the same error.

```bash
Running in KRaft mode...
CLUSTER_ID is required.
Command /usr/local/bin/dub ensure CLUSTER_ID] FAILED !
```
### Root Cause
KRaft mode (introduced in Kafka 2.8, production-ready in 3.3+) eliminates Zookeeper dependency but requires a unique cluster identifier for metadata quorum formation. This CLUSTER_ID must be set before first boot and is not auto-generated by Confluent images.

### Solution
Added CLUSTER_ID environment variable to docker-compose.yml:
```bash
environment:
  CLUSTER_ID: 'MkU3OEVBNTcwNTJENDM2Qk'  # Base64 cluster ID
```
**Note:** The cluster ID is a random base64 string. For production,generate using: Kafka-storage random-uuid

### Additional Configuration Required
KRaft mode also required fixing these related configuration issues:
- KAFKA_CONTROLLER_LISTENER_NAMES (was misspelled as KAFKA_CONTROLLER_LIST_NAME)
- Correct volume path: /var/lib/kafka/data (not /opt/kafka/data)
- KAFKA_PROCESS_ROLES: broker,controller (for single-node deployment)

### Prevention for Future
- Always validate KRaft configuration against Confluent documentation
- Check docker logs immediately when container shows 'Restarting' status
- Use docker inspect to verify environment variables are actually set
- Store cluster ID in secrets management (Vault, AWS Secrets Manager) for production

## Issue 3: Bytes Not JSON Serializable

### Symptom

Consumer successfully connected to Kafka and received messages, but every message was immediately routed to Dead Letter Queue (DLQ) with the following exception:
```bash
TypeError: Object of type bytes is not JSON serializable
File 'storage/gcs/raw_writer.py', line 23, in write_raw_record
```
### Root Cause
Kafka message headers are returned by confluent-kafka Python client as raw bytes objects. When constructing the record dictionary for GCS write, these bytes values were passed directly to json.dumps(), which cannot serialize bytes without explicit encoding

### Critical Contract:
Kafka wire protocol transmits everything as bytes (keys, values, headers). Client libraries require explicit decoding to strings. This is by design for protocol efficiency and schema flexibility.

### Original Code (Broken)
```bash
headers = dict(msg.headers() or [])
# headers contains bytes values → json.dumps() fails
```

### Solution
```bash
headers = {
    k: v.decode('utf-8') if isinstance(v, bytes) else v
    for k, v in (msg.headers() or [])
```
This dict comprehension decodes bytes values to UTF-8 strings while preserving any string values that may already be decoded.

### Why This Matters
- Keys and values are typically decoded explicitly in consumer code
- Headers are often overlooked because they're optional metadata
- Error only surfaces when headers are actually present in messages
- Silent failure if headers are empty -> passes early testing but fails in production

### Prevention for Future
- Always decode bytes explicitly: keys, values, AND headers
- Add exception logging with traceback.print_exc() during development
- Test with messages that have headers populated (not just empty headers)
- Consider using schema registry or Avro for strongly-typed serialization
